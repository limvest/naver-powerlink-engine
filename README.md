# 네이버 파워링크 키워드 관리·자동 입찰 엔진

네이버 검색광고(파워링크)의 키워드를 대량으로 등록·심사 추적·운영하고, 실제 검색 결과에서 광고 순위를 관측해 입찰가를 자동으로 조정하는 엔진입니다. 수만 개 키워드를 사람이 광고 관리 화면에서 하나씩 다룰 수 없어서 만들었습니다.

> **공개본 안내** — 법률사무소용 광고 서비스([law-firm-naver-ads-management](https://github.com/limvest/law-firm-naver-ads-management))에서 키워드 관리와 입찰 부분만 떼어 낸 저장소입니다. 광고주·경쟁사 이름, 도메인, 계정 ID, 연락처는 가상 값이고, 코드와 테스트 안의 예시 사건명도 가상 이름입니다.

## 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 기간 | 2026년 8월 ~ 10월 |
| 한 일 | 검색광고 API 연동, 키워드 대량 등록·심사·운영, 순위 관측, 자동 입찰 정책과 실행 파이프라인 |
| 기술 | TypeScript, Node.js, PostgreSQL, Drizzle ORM, Vitest |
| 규모 | 코드 약 1만 2천 줄, 테스트 247개, DB 테이블 15개 |
| 안전장치 | 기본값은 미리보기(dry-run), 실제 반영은 상한가와 변경 건수를 명시해야 실행 |

## 어떤 문제를 풀었나

사건명 하나하나가 광고 키워드가 되는 서비스라 키워드가 수만 개였습니다. 여기서 세 가지가 어려웠습니다.

- **등록**: 키워드마다 광고그룹, 소재, 랜딩 주소를 맞춰 등록하고 심사 결과를 추적해야 합니다.
- **잡음**: 수집된 키워드 후보에는 무작위 문자열, 도메인 조각, 일반 명사가 섞여 있어 그대로 등록하면 광고비가 샙니다.
- **입찰**: 키워드마다 경쟁 상황이 달라 입찰가를 일괄로 정할 수 없고, 올려야 할 곳과 내려도 되는 곳을 가려야 합니다.

## 구성

```text
키워드 후보 ─▶ 선별 ─▶ 대량 등록 ─▶ 심사 동기화 ─▶ 운영(올리기/내리기, 운영 시간)
                                                        │
                                  순위 관측 ◀───────────┘
                                      │
                 스냅샷 ─▶ 자격 판정 ─▶ 추정 ─▶ 결정 ─▶ 예산 확인 ─▶ 반영 ─▶ 검증 ─▶ 보고
```

### 1. 검색광고 API 연동 — `src/lib/engine/naver/`

- `client.ts`, `signature.ts`: 요청마다 HMAC-SHA256 서명을 붙이는 API 클라이언트.
- `channel.ts`: 광고주 도메인과 비즈채널을 맞춰 보는 공용 규칙.
- API 키와 시크릿은 AES-256-GCM으로 암호화해 DB에 저장합니다 (`src/lib/engine/cred-crypto.ts`).

### 2. 키워드 관리

| 기능 | 파일 | 내용 |
| --- | --- | --- |
| 선별 | `naver/exact-keyword.ts` | 25자 제한, 무작위 문자열·도메인 조각·URL 조각·일반 명사·반복 문구를 사유와 함께 거름 |
| 등록 계획 | `registration-plan.ts` | 등록 대상, 소재 문구, 랜딩 주소를 묶어 계획을 만듦. 차단 목록과 금지 표현 검사 포함 |
| 등록 실행 | `register-run.ts` | 캠페인 → 광고그룹 → 키워드 → 소재 순으로 반영. 실패하면 상태를 되돌리고 사유를 남김 |
| 대량 캠페인 | `naver/bulk-search-run.ts`, `naver/segmented-search-run.ts` | 수만 개 키워드를 여러 광고그룹으로 나눠 등록하고 기존 등록분과 맞춤 |
| 심사 동기화 | `review-sync.ts`, `naver/exact-review-sync.ts` | 심사 결과를 반영하고 차단 키워드를 중지 |
| 올리기/내리기 | `reconcile-ads.ts` | 광고주가 고른 노출 의사를 광고그룹 잠금 상태에 반영 |
| 운영 시간 | `naver/ad-hours.ts` | 한국 시간 08~22시에만 광고를 켬 (종일 운영 옵션 있음) |
| 소재 | `ad-copy.ts`, `naver/responsive-material.ts` | 파워링크 소재와 반응형 소재 생성 |
| 통계 | `src/platform/integrations/naver-searchad.ts` | 노출·클릭·비용 통계 응답 해석 |

키워드 상태는 정해진 전이만 허용합니다 (`state.ts`).

```text
subscribed ─▶ ad_pending ─▶ ad_registered ─▶ live
                  │               │            │
                  ▼               ▼            ▼
              rejected          paused ◀───────┘
```

### 3. 자동 입찰 — `programs/naver-auto-bid/`

실제 검색 결과에서 내 광고가 몇 번째에 나오는지 관측하고, 목표 순위에 맞춰 입찰가를 조정합니다.

- **순위 관측** (`rank-observer.ts`): PC·모바일 파워링크 영역을 읽어 광고주 도메인의 위치를 찾습니다.
- **정책** (`policy.ts`): 하한가, 상한가, 한 번에 올리고 내릴 수 있는 폭, 변경 후 대기 시간을 지키며 올림·내림·유지를 결정합니다.
- **요청 속도 제어** (`rate-limiter.ts`): 깨끗한 응답이 쌓이면 속도를 올리고, 차단·오류 응답이 오면 간격을 두 배로 늘립니다.
- **기록** (`repository.ts`): 결정은 요청 전에, 결과는 요청 후에 저장합니다. 같은 실행 키로 다시 돌려도 중복 반영하지 않습니다.
- **검증**: 반영한 묶음은 다시 조회해 입찰가가 실제로 바뀌었는지 확인합니다.
- **순위 학습** (`rank-learning.ts`, `continuous-scheduling.ts`): 키워드별로 최근 관측 24건을 요약해 두고, 같은 결과가 연속으로 확인될 때 판단에 반영합니다. 다음 관측 시점과 우선순위도 여기서 정합니다.

기본 설정값은 다음과 같습니다.

| 설정 | 기본값 |
| --- | --- |
| 목표 순위 | 3위 |
| 하한가 | 70원 |
| 상한가 | 입찰 명령은 기본값 없음(실제 반영 시 반드시 지정). 연속 실행 파이프라인은 지정하지 않으면 3,000원 |
| 한 번에 올리는 폭 / 내리는 폭 | 100원 / 10원 |
| 변경 후 대기 | 6시간 |
| 순위 관측 한도 | 실행당 50,000건, 분당 3,000건, 동시 64건 |

설계 배경과 운영 중 측정값은 [`SYSTEM_DESIGN.md`](programs/naver-auto-bid/SYSTEM_DESIGN.md)에, 단계별 계획은 [`PLAN.md`](programs/naver-auto-bid/PLAN.md)에, 명령 사용법은 [`programs/naver-auto-bid/README.md`](programs/naver-auto-bid/README.md)에 있습니다.

## 안전장치

돈이 나가는 시스템이라, 실수로 반영되지 않게 하는 데 가장 공을 들였습니다.

1. **입찰 명령의 기본은 미리보기입니다.** `--live`를 주지 않으면 광고 계정에 쓰지 않습니다. 환경변수로는 켤 수 없습니다.
2. **상한가와 변경 건수를 명시해야 합니다.** `--live`는 `--ceiling`과 `--max-changes`가 함께 있어야 실행됩니다.
   연속 실행 파이프라인(`competitor-pipeline.ts`)은 `--confirm-live`가 있어야 돌고, 매 실행 전에 DB의 입찰 정책이 켜져 있는지와 운영 시간대인지 확인합니다.
3. **올릴 수 없는 키워드는 건드리지 않습니다.** 심사 중·반려·중지·차단 상태의 키워드는 입찰 대상에서 뺍니다.
4. **캠페인과 광고그룹의 노출 상태, 랜딩 주소는 바꾸지 않습니다.** 입찰가만 다룹니다.
5. **동시에 두 번 돌지 않습니다.** 같은 광고주에 대한 실행이 겹치면 거부합니다.
6. **속도 제한 응답(429)을 받으면 계정 전체가 쉬었다가 다시 시도합니다.**
7. **광고 클릭은 자동화하지 않습니다.** 무효 트래픽과 과금, 플랫폼 정책 문제를 만들 수 있어 범위에서 뺐습니다.

키워드 관리 쪽에서는 등록, 올리기/내리기, 심사 반영, 대량 동기화, 소재 교체 명령이 `ENGINE_LIVE=1`이 있어야 광고 계정에 씁니다. 운영 시간 적용과 키워드 차단 명령에는 이 확인이 없습니다.

## 실행

```bash
npm install
npm test             # 테스트 247개. 내장 PostgreSQL(PGlite)을 써서 별도 DB가 필요 없습니다
npm run typecheck
```

실제 DB와 광고 계정에 연결하려면 `.env.example`을 참고해 환경변수를 채우고, `drizzle/0000_init.sql`로 테이블을 만듭니다.

```bash
# 입찰 미리보기 (광고 계정에 쓰지 않음)
npm run naver:auto-bid -- --firm 1001

# 한 단계만 미리보기
npm run naver:auto-bid -- --firm 1001 --stage decide

# 실제 반영: 상한가와 변경 건수를 반드시 명시
npm run naver:auto-bid -- --firm 1001 --live --ceiling 800 --max-changes 10
```

## 원래 서비스에서 가져오지 않은 것

- 광고주용 대시보드와 운영자 화면 (웹 UI)
- 일별 광고 성과를 DB에 쌓는 동기화 작업
- 입찰 전략 기록을 보는 로컬 대시보드와 그 운영 기록
- 서버 예약 실행 설정 (systemd 타이머)과 단계별 실행을 감싸는 셸 스크립트

DB 스키마는 원래 서비스의 70개 테이블 중 이 엔진이 쓰는 15개만 남기고, 마이그레이션을 하나로 새로 만들었습니다.

## 배운 점과 한계

- **자동화의 핵심은 멈추는 조건이었습니다.** 입찰 로직보다 "언제 쓰지 않을 것인가"를 정하는 코드가 더 많습니다. 입찰 명령에서 상한가를 기본값 없이 필수로 둔 것도 그 때문입니다.
- **추정치 대신 관측값을 기본으로 삼았습니다.** 광고 플랫폼이 주는 예상 입찰가는 보조 전략으로 남기고, 실제 검색 결과의 순위를 읽는 방식을 기본 전략으로 뒀습니다.
- **빠르게 읽는 것과 안정적으로 읽는 것은 다릅니다.** 운영 중 시험에서 분당 3,000건을 요청했을 때 실제 처리량은 그보다 낮았고, 지속 가능한 속도는 확인하지 못했습니다. 측정값은 설계 문서에 그대로 적었습니다.
- **한 광고주 계정을 기준으로 만든 부분이 남아 있습니다.** 운영 시간, 캠페인 이름 규칙, 광고그룹 분할 기준에 특정 계정을 가정한 값이 있어, 다른 계정에 쓰려면 설정으로 빼야 합니다.
- **순위 관측은 검색 결과 화면 구조에 의존합니다.** 화면 구조가 바뀌면 관측이 실패하며, 이 경우 입찰에 쓰지 않고 실패로 처리합니다.
